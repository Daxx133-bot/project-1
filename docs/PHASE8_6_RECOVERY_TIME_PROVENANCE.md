# Phase 8.6: Recovery Time Provenance

This document traces the exact origin and implementation of the `recovery_time_s` metric as found in the primary analysis dataset.

## Claim vs. Reality

**Previous Manuscript Claim:**
> "Calculated as the elapsed time (in seconds) from the end of the fault-injection window until the application's overall error rate and 95th percentile latency stabilized continuously within a 10% tolerance threshold of their respective pre-fault baseline medians for a minimum of 10 consecutive seconds. Capped at 60 seconds."

**Actual Implementation Reality:**
> Polling `docker inspect` every 2 seconds until the container reports its state as running.

## Exact Implementation Details

The metric `recovery_time_s` is generated by the `restore_service()` function in `faultinjection/fault_runner.py` (Lines 190-238).

### Start Timestamp Definition
The recovery timer starts immediately before attempting to restart the container (for `kill` faults) or immediately after printing the auto-expiration warning (for `cpu` and `latency` faults).
```python
start = time.time()
```

### Recovery Condition
The system polls the Docker daemon to check if the specific container is running:
```python
result = subprocess.run(
    [docker_exe, "inspect", "--format", "{{.State.Running}}", container_name],
    capture_output=True, text=True, check=True,
)
if "true" in result.stdout.lower():
    recovery_time = time.time() - start
```

### Polling Frequency
The script polls the Docker socket once every **2 seconds**.
```python
time.sleep(2)
```

### Timeout
There is a hardcoded timeout of **60 seconds**.
```python
max_wait = 60  # seconds
```

### Units
Seconds (floating point, rounded to 2 decimal places before logging).

### Zero-Value / Missing Behavior
- If the `docker inspect` command fails or returns false for 60 seconds, it falls through the loop and returns `60.0`.
- There is no scenario where it natively returns `0.0` or missing unless the `start` and end timestamps evaluate instantly.

## Conclusion

The `recovery_time_s` metric measures **container process restart time**, NOT telemetry stabilization.

For `cpu` and `latency` faults, the Pumba sidecar container auto-expires. The target service's container never actually stops running. Therefore, `docker inspect` will return `true` on the very first poll, leading to a `recovery_time_s` effectively measuring the overhead of a single `subprocess.run()` call (~0.01s - 2.0s).

This explains why `cpu` and `latency` faults have near-zero correlations across all metrics for `recovery_time_s` in the Social Network — the metric was returning near-constant near-zero values for those fault types because the container never died.
